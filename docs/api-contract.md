## Identity and scope

A **Manufacturing site** is one physical production location served by a Neuradix Manufacturing
deployment. It is not a Frappe site: the Frappe site is the ERP instance (reported as
`source.instance`). In this contract version a Manufacturing site maps to exactly **one ERPNext
Company and one warehouse subtree** (a `Neuradix Manufacturing Site` record with a `root_warehouse`).
One ERP instance can serve several Companies and sites; one Company can have several sites with
non-overlapping subtrees. The mapping cannot be edited after creation; changing it means a new site ID.
Overlap is validated when a site is saved and re-checked on every request: if later warehouse
re-parenting nests one site's subtree in another's, both sites are refused (403) until repaired.

A Work Order belongs to a site when its Company is the site's Company, it is submitted or cancelled,
its Target Warehouse is in the subtree, and its Work-In-Progress Warehouse is empty or also in the
subtree. Default source and scrap warehouses may be shared stores and do not decide membership.
An order spanning two sites belongs to neither.

The **integration principal** is a dedicated Frappe user that holds only the
`Neuradix Integration Reader` role (desk access off) and has an enabled
`Neuradix Integration Principal` record listing its sites. Scope is resolved on the server from the
authenticated user on every call. Request parameters can select one of those sites but never add a
site, Company or warehouse; unknown parameters are ignored by Frappe and cannot widen scope.
Administrator and System Manager are bootstrap identities and are **not** integration principals.
A principal is refused if its user is disabled, its record is disabled, it holds any other role,
or the requested site is unknown, disabled or not listed — all with the same `PermissionError`.
See [integration identity](integration-identity.md) for provisioning and revocation.

The role grants read on Work Order through one Custom DocPerm and nothing else. Three layers
keep it narrow:

1. **Route allowlist.** An `auth_hooks` entry runs after Frappe authenticates each request and
   refuses (403) every request from a user holding the role except a plain `GET` to the four
   methods below on `/api/method/` or `/api/v1/method/`. `/api/resource`, `frappe.client.*`
   (including the `validate_link` and `get(filters=...)` existence oracles), report view,
   search, `/api/v2`, `cmd` dispatch, desk pages and private files are closed to principals.
2. **Frappe permission hooks.** `permission_query_conditions` (Work Order and its Work Order Item
   and Work Order Operation child rows) and a deny-only `has_permission` hook confine the role to
   the principal's sites on every in-process read path.
3. **Explicit filters.** The methods below select with the site's Company, lifecycle and warehouse
   filters and re-check membership. Document sharing, which Frappe lets override a denying hook on
   single-document checks, therefore cannot widen their results.

## Methods

All methods are authenticated `GET` requests to `/api/method/neuradix_manufacturing_erpnext.api.v1.<method>`.
Use Frappe token authentication (`Authorization: token <api_key>:<api_secret>`) held server-side.
Frappe returns the payload inside `message`. Query-string values are strings.

| Method | Parameters | Returns |
|---|---|---|
| `capabilities` | — | Capability profile; `principal` lists the caller's sites (null for bootstrap administrators) |
| `work_orders` | `site` (required), `page_size` 1–200 (default 50), and either `modified_since` (RFC 3339 with offset, inclusive) or `cursor` | One page of submitted and cancelled orders ordered by (`modified`, `name`) |
| `work_order` | `site`, `name` | One order with required-item and operation rows |
| `work_order_deletions` | `site`, `page_size`, and either `deleted_since` or `cursor` | Deletion markers for orders that were in the site when deleted |

| Condition | HTTP | `exc_type` |
|---|---|---|
| No credentials (Guest) | 403 | PermissionError |
| Invalid API key or secret, or disabled user | 401 | AuthenticationError |
| Not a principal, extra role, disabled principal, or unauthorized/unknown/disabled site | 403 | PermissionError |
| Principal calling any other route, or any method other than GET | 403 | PermissionError |
| Order missing, draft, or outside the site | 404 | DoesNotExistError (identical for all cases) |
| Invalid `page_size`, cursor, timestamp or cursor+since combination | 417 | ValidationError |
| Companion not installed or method missing on that ERP | 417 | ValidationError (Frappe's "failed to get method"); check `capabilities` first |
| Stored ERP value outside the contract (for example a negative or over-wide quantity) | 500 | ContractDataError; the page fails instead of skipping the record |

## Work Order DTO rules

- `name` is the ERP document identifier. A global reference is (`source.instance`, `company`, `name`).
- `lifecycle` is `submitted` (docstatus 1) or `cancelled` (docstatus 2). Drafts are never exposed.
- `status` normalizes ERPNext's status (`not_started`, `in_process`, `completed`, `stopped`,
  `closed`, `cancelled`, `submitted`); unrecognized values are `unknown` and `erp_status` keeps the
  raw text. ERPNext Stopped, Closed and Completed are ERP facts, not Manufacturing operational close.
- Quantities are exact strings from DECIMAL(21,9) columns read with `CAST(... AS CHAR)`: no float,
  no exponent, no trailing fraction zeros, at most 12 integer and 9 fraction digits. All Work Order
  and required-item quantities are in the respective `stock_uom`; ERPNext stores no other unit here.
- Timestamps are ERP wall-clock values labelled with the ERP system time zone offset
  (`source.erp_time_zone`), always with six fraction digits. They are ERP time, not site time.
  Date-only fields stay `YYYY-MM-DD`. In a repeated DST hour the first occurrence is used.
- `version` is the exact stored `modified` value in fixed-width `YYYY-MM-DD HH:MM:SS.ffffff`
  form, so string order equals stored order. Use it to detect and order changes, not as a clock.
- `amended_from` names the cancelled order this one amends, only when that order is in the same
  site; otherwise it is null. A replacement is found through `amended_from` on the amending order.
- BOM, Item, Warehouse, Workstation and Operation are referenced by name only. Linked records are
  not read with raised privileges. A changed BOM appears as a different `bom_no` (a draft edited
  before submission, or an amendment whose `amended_from` names the cancelled order).

## Incremental refresh

1. Start a pass with `modified_since` = (latest `modified_at` already applied) minus
   `sync.recommended_overlap_seconds` (3900 s) from capabilities, or omit it for a full scan.
2. Follow `next_cursor` until it is null. A cursor is opaque, bound to its method and site, and
   carries position only; scope is re-checked on every call.
3. Upsert items by `name`; ignore an item whose `version` equals the stored one. Do not advance a
   stored watermark past a record that failed to apply.
4. Read `work_order_deletions` the same way. Apply a marker only when the stored record's
   `version` is not newer than the marker's `last_version`: Frappe can reuse a deleted order's
   name (its naming series steps back), and a newer stored version belongs to the new order.
   Restored deletions are also reported, because Frappe restores a cancelled order as a draft,
   which is no longer exposed.
5. Run a periodic full scan and treat orders absent from it as no longer in scope.

The overlap covers long transactions committing an older `modified` late and the repeated local
hour when the ERP zone leaves DST. A page may hold fewer than `page_size` items while `next_cursor`
is non-null. Full reconciliation is required because ERPNext and Frappe change or remove data
without a new `modified` value in some paths:

- required-item `transferred_qty`, `consumed_qty` and `returned_qty` are written with
  `update_modified=False` by `update_required_items`; refresh the detail of active orders before
  relying on material quantities;
- Item or Company renames rewrite references without touching `modified`;
- an order moved out of a site (for example by re-parenting a warehouse) simply stops appearing;
- company transaction deletion removes rows without Deleted Document markers, and old Deleted
  Document rows can be purged.

The deletion scan is filtered to the site's Company, lifecycle and warehouses in SQL, so a cursor
only ever refers to the site's own deletion markers.

## Compatibility and versioning

Additive fields, removed fields and changed meanings all change the payload `schema` or the
contract version while the contract is a draft. Manufacturing rejects unknown fields and exact
version mismatches until 1.0 so drift fails loudly in tests rather than in production. A breaking
change publishes a new `.vN` schema alongside the old one where a migration window is needed.
Release tags of both repositories are recorded in the compatibility matrix before pilots.

## Not implemented

No method creates, submits, cancels or posts any ERP document. Stock posting, production posting,
maintenance synchronization and command outcome discovery remain `false` in capabilities and are
EN-02 onward. The business command envelope (stable command ID, idempotency key, payload conflict
detection, outcome lookup) is planned and not advertised as an endpoint.

No PLC or robot credentials, control methods or direct actuator calls belong in this app.
Machine tasks always pass from Manufacturing through Neuradix Robotics Platform.
